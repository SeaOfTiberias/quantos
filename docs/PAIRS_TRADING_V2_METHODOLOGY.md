# Pairs Trading v2 — Roll-Adjustment + Corporate-Action Fix, Pre-Committed 2026-07-27 Before Any Result Exists

## Why this exists

Candidate 12 (`docs/PAIRS_TRADING_METHODOLOGY.md`) FAILED its pre-registered
bar (pooled PF 0.94, Sharpe -0.17, `docs/PAIRS_TRADING_RESULTS.md`).
Fable's independent review (2026-07-26, `quantos_pairs_trading_status`
memory) confirmed the FAIL is trustworthy — stripping every trade touched
by a confirmed bug barely moves net P&L (-Rs 3,593,624 vs -Rs 3,819,293)
— but found two real, previously undisclosed construction bugs, neither of
which explains the fold 6-8 collapse but both of which Fable explicitly
recommended fixing **before any future pairs-trading candidate**:

1. **No corporate-action jump guard.** 25 real unadjusted split-style jumps
   across the futures universe, 13 in-universe, tainted 17 of 4705 trades.
   Inflated folds 4-5's apparent edge (fold 4 is 47% one lucky jump-trade)
   rather than explaining the real collapse.
2. **Unadjusted futures-roll splicing.** The original methodology
   deliberately built no continuous/back-adjusted series ("No back-adjusted
   continuous series is built" — a disclosed, pre-registered simplicity
   choice at the time). Fable measured this directly: rollover days average
   1.82% absolute move (median 1.44%) vs 1.41%/1.02% on normal days, across
   5,776 vs 116,437 observations — a real ~30-40% systematic inflation in
   typical move size on roll days, present continuously in every symbol's
   series, likely inflating the frozen formation-window `spread_std` and
   hedge-ratio estimate project-wide (not isolated to specific flagged
   trades the way the corp-action bug is).

**This is a bug-fix re-run, not a new hypothesis.** Every other design
choice from `docs/PAIRS_TRADING_METHODOLOGY.md` is held fixed — same
universe construction, same Engle-Granger test, same 6-month
formation/3-month trading walk-forward with a FROZEN per-fold hedge ratio
(no intra-window re-estimation; that would be a separate, additionally-
justified change, not bundled in here — "one variable at a time," same
discipline as the turnover ablation's quarterly-only cadence choice), same
entry/exit rules, same cost model. Only the two confirmed bugs are fixed.
If the verdict is still FAIL after this, that is a strong, clean signal —
neither known construction flaw was responsible. If it flips to PASS,
that's equally informative: the original FAIL was largely an artifact of
these two bugs, not a real absence of edge.

**Do not edit this file after the validation has run.**

## Fix 1 — Corporate-action jump guard

Reuses `core/rotation/reconstitution_gutcheck.py`'s `_has_corporate_action_jump`
logic exactly (same ratio band, `(0.5, 2.0)` on consecutive-day closes) —
not reimplemented, imported directly, so the definition of "suspected
corporate action" can't silently drift between the two modules.

**Why the same threshold is safe for futures (not just cash equity):** a
genuine roll-day price change (Fix 2's problem) averages ~1.8%, nowhere
close to tripping a ratio outside `[0.5, 2.0]` (i.e., a >100% jump or >50%
drop) — this guard and the roll-adjustment fix are catching two
structurally different, non-overlapping magnitudes of price discontinuity,
not the same phenomenon twice.

**Application**: for each candidate pair in each fold, check every symbol's
RAW (not adjusted) daily close series for a flagged jump within the
formation window AND separately within the trading window. A pair with
either leg flagged in either window is excluded from that fold entirely —
same "simply not traded that fold" pattern the cointegration test-failure
path already uses, not a partial/patched trade.

## Fix 2 — Futures-roll back-adjustment (point-in-time-safe, forward-built)

**The core design constraint**: the adjustment applied to day `t`'s price
must depend ONLY on roll events that have already happened on or before
`t` — never on a later roll. A conventional "backward-adjusted continuous
contract" (anchor to the most recent price, scale history backward) would
violate this for a walk-forward backtest: a formation window in early 2024
would get its prices adjusted using roll ratios from rolls that hadn't
happened yet as of that window, a real lookahead bug. This design instead
builds the adjustment **forward** from the first day of the series.

**Data requirement**: on top of each day's near-month close (already
parsed), also capture that same day's **next-nearest-expiry close** (the
contract that will become near-month after the current one expires) —
`core/pairs/universe.py`'s raw bhavcopy parse already has every listed
expiry available per symbol per day; this just keeps a second field
instead of discarding it.

**Construction** (in log-price space, matching the cointegration test's
own convention):

```
adj_close[0] = close[0]  (first day of the series, no adjustment needed)
offset[0] = 0.0

for i in 1..n-1:
    if expiry[i] == expiry[i-1]:            # no roll — same contract as yesterday
        offset[i] = offset[i-1]
    else:                                     # roll happened between day i-1 and day i
        # roll ratio measured on day i-1, the LAST day both the old (near-month)
        # and new (next-month) contracts were simultaneously observed —
        # never measured post-expiry, when the old contract no longer trades.
        roll_log_diff = log(next_month_close[i-1]) - log(near_month_close[i-1])
        offset[i] = offset[i-1] - roll_log_diff

    adj_close[i] = exp(log(close[i]) + offset[i])
```

**Why this is correct, not just plausible**: on a roll day, `adj_close[i] /
adj_close[i-1]` works out to `close[i] / next_month_close[i-1]` — the real
one-day return of the contract that WAS next-month yesterday and IS
near-month today, i.e., the actual economic price change of a single,
continuously-held (synthetic) position, with the pure contract-switch
artifact removed. On a non-roll day, `adj_close[i]/adj_close[i-1] =
close[i]/close[i-1]` exactly — identical to the raw series, so Fix 2 only
touches the handful of actual roll days, not the whole series.

**Fallback (disclosed, not silently absorbed)**: if `next_month_close[i-1]`
is unavailable (a real but rare gap — e.g., the next contract not yet
listed with a settled price that day), that specific roll seam is left
UNADJUSTED (`offset[i] = offset[i-1]`, equivalent to the original
candidate 12 behavior for that one seam only). Count of unadjusted seams
is reported in the results doc, not hidden inside an otherwise-clean
number.

**What `adj_close` is used for, and what it is NOT used for** — this is
the one rule that matters most in this doc:

- **Formation-window cointegration test** (OLS hedge ratio, ADF test,
  spread mean/std): uses `adj_close`. This is the whole point of the fix —
  an un-spliced series so a roll seam inside a 6-month formation window
  doesn't inflate `spread_std` or distort the estimated hedge ratio.
- **Trading-window z-score** (`z_t = (spread_t - formation_mean) /
  formation_std`): `spread_t` is computed from `adj_close`, for the same
  reason — a roll seam inside the trading window must not manufacture a
  false z-score spike that triggers a fake entry or a fake "reverted" exit.
- **Actual trade fill prices, P&L, and transaction costs**
  (`entry_price_a/b`, `exit_price_a/b` in `PairTrade`, and everything
  `core/pairs/costs.py` computes from them): uses **raw** `close`, always.
  A trader cannot fill an order at a synthetic back-adjusted price — real
  money enters and exits at the real near-month contract's real price.
  Mixing adjusted prices into the P&L calculation would replace one
  artifact (roll-seam noise) with a different one (fictitious fills).

## What stays identical to candidate 12 (not touched in this pass)

- Universe construction, sector tagging, same-sector-only pairing.
- Engle-Granger test itself (OLS + ADF, p<0.05, no multiple-testing
  correction — same disclosed limitation).
- 6-month formation / 3-month trading walk-forward schedule, **frozen
  hedge ratio and spread mean/std for the entire trading window** — no
  intra-window re-estimation. (A rolling/adaptive hedge ratio that updates
  DURING the trading window is a real, separately-motivated idea — Fable's
  own read of the fold 6-8 collapse as "more consistent with genuine
  signal decay, a real regime shift" than either bug points toward it —
  but it is a NEW hypothesis, not a bug fix, and does not belong bundled
  into this pass. If this re-run's verdict doesn't resolve the fold 6-8
  question, that idea is the natural next candidate, pre-registered
  separately.)
- Entry/exit rules (z=2.0 entry, 0.0 exit, 20-trading-day max hold,
  force-close 3 days before near-month expiry).
- Cost model (`core/pairs/costs.py`), sizing convention (₹100,000 notional
  per leg).
- Pass bar: `core/backtest/parser.py`'s `has_positive_edge` (PF > 1.0 AND
  Sharpe > 0.5), pooled trading-window trades, net of costs — same
  convention as candidate 12, reported with the same per-fold breakdown.

## What would make this validation untrustworthy after the fact

- Changing the corp-action ratio band, the roll-adjustment construction, or
  reverting to using `adj_close` for fills/costs (or vice versa) after
  seeing a weak or strong result.
- Adding intra-window hedge-ratio re-estimation in the same pass — that is
  a separate hypothesis, not a bug fix, and would confound "did fixing the
  known bugs change the verdict" with "did adaptive re-estimation change
  the verdict."
- Reporting only the pooled result while omitting the per-fold breakdown,
  especially folds 6-8 (the original collapse) — those folds are the
  direct test of whether these fixes were the actual cause.
- Cherry-picking which of the two fixes to apply based on which one moves
  the number in a favorable direction — both are confirmed real
  construction flaws per Fable's review; both are fixed together, as a
  single re-run.
