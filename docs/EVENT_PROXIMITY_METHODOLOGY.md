# Known-Event Proximity vs Forward Realized Vol — Methodology, Pre-Committed 2026-07-27 Before Any Result Exists

## Why this exists, and why it is NOT vol-conditioning attempt #5

Vol-conditioning closed for good, 4-for-4, this same session
([[quantos_regime_signal_redesign_plan]],
[[quantos_term_structure_4th_attempt_and_vision_fork]]) — four
independently-constructed CONTINUOUS statistics (VIX level, IV-minus-RV,
option skew, ATM IV term structure), all Fable-confirmed to reproduce the
same non-monotonic "smile" artifact, most likely a property of forward
realized vol's own fat-tailed/episodic structure rather than real
information in any of those signals. Fable's explicit recommendation: no
5th attempt at reshaping that same residue.

**This is not that.** Every prior signal was a *continuous, statistically
inferred* quantity, bucketed into data-driven quintiles — exactly the
construction that makes it easy for a handful of real vol-shift days to
land in both tails of an otherwise-noisy split, regardless of whether the
underlying statistic carries information. This signal is different in
kind: **a binary flag for calendar proximity to a small set of
PUBLICLY KNOWN, ADVANCE-PUBLISHED event dates** (RBI rate decisions, Union
Budget) — not inferred from same-day price/IV data at all, and not
quintile-bucketed (too few event days to support 5 buckets meaningfully;
see sample-size note below). It also carries essentially zero lookahead
risk of any kind: these dates are published months in advance by the RBI
and the Government of India, so "knowing" an event is imminent 5 trading
days out is not an information leak — a live system would have known it
too, on that same historical day.

Proposed and scoped this session after the user pushed back on treating
vol-conditioning's closure as the end of the regime-aware-dashboard
vision — see [[quantos_term_structure_4th_attempt_and_vision_fork]]'s
"strategic fork" section. The honest scoping insight: before investing in
an LLM layer that reads qualitative commentary around events, first check
whether bare proximity to a KNOWN event predicts elevated forward
volatility at all. If it doesn't, an LLM reading news on top of it isn't
likely to rescue that — same logic this project has applied throughout
(don't ML-wrap a signal that doesn't work).

**Do not edit this file after the validation has run.**

**Mandatory sequencing, same standing rule as every prior signal doc in
this project:** validated fully against real forward realized volatility
first. Not checked against VRP's already-failed trade data or any
strategy backtest before this validation's own verdict locks.

## Event calendar — sourced this session, not assumed

The existing `core/events/calendar.py::load_macro_calendar_2026()` only
covers 2026 (built for live-signal blocking, not historical backtesting)
and does not reach back to 2024, so a fresh calendar was assembled and
verified against real sources for this validation's 2024-01-01 to
2026-07-27 window. **RBI Monetary Policy Committee resolution date is
used as the event date (the 3rd day of each 3-day meeting, when the rate
decision is actually announced — the market-moving day, not the meeting's
start)**:

- **2024**: Feb 8, Apr 5, Jun 7, Aug 8, Oct 9, Dec 6 — sourced from RBI's
  own official FY2024-25 schedule press release (fetched directly,
  `rbi.org.in/Scripts/BS_PressReleaseDisplay.aspx?prid=57580`) plus the
  Feb 2024 meeting (last of FY2023-24, "47th MPC meeting... February 6 to
  8, 2024").
- **2025**: Feb 7, Apr 9, Jun 6, Aug 6 (rescheduled from the originally
  announced Aug 5-7), Oct 1 (meeting held Sep 29-Oct 1), Dec 5 — sourced
  from RBI's FY2025-26 schedule announcement and its August reschedule
  notice.
- **2026**: Feb 6, Apr 8, Jun 5 — reused as-is from the existing
  `core/events/calendar.py` hardcoded 2026 calendar (already live
  production infra, not re-verified independently this session; only
  needed through mid-2026 given the backtest window ends 2026-07-27 and
  the forward-RV label needs 20 trading days of runway after the last
  scored day).

**Union Budget dates**:
- **2024**: Feb 1 (interim, pre-election) AND **Jul 23** (the full
  FY2024-25 budget, presented after the general election formed the new
  government — verified separately, not assumed, since this is a less
  obvious date than the routine Feb 1 pattern).
- **2025**: Feb 1.
- **2026**: Feb 1.

**Explicitly out of scope for this pass**: NSE index rebalancing
(semi-annual, ~end of March/September). Already in the existing
2026-only calendar as a MEDIUM-impact event, but assembling verified
historical *effective* dates (as opposed to announcement dates) for every
2024-2026 cycle would need more research than this event type's a priori
plausibility as an INDEX-level vol driver justifies — a rebalance mainly
moves the specific added/removed constituents' single-stock volume, not
obviously the whole index's realized vol the way a rate decision or
budget does. If wanted later, this needs its own addendum with its own
verified date list, not a guess folded into this pass.

## Event window

**A trading day `t` is an "event day" if it falls within 1 calendar day
of any event date** (i.e., `abs((t - event_date).days) <= 1`) — a
symmetric [-1, +1] window, the standard event-study convention, capturing
same-day reaction plus one day of immediate before/after. Pre-registered
as a fixed choice, not tuned after seeing results. Wider anticipation
windows (e.g., ±5 days) or narrower same-day-only windows are explicitly
NOT tried in this pass — if this fails, that is not grounds for a window
sweep in the same session (same "no retroactive loosening" discipline as
every prior methodology doc).

## Realized-vol construction (the forward outcome being predicted)

Identical to all 4 prior vol-conditioning signals, for direct
comparability: 20 trading days, close-to-close, annualized (`×
sqrt(252) × 100`), from the same bhavcopy `underlying_close` series
(`scripts/validate_vol_skew_signal.py`'s already-built fetch/parse,
reused directly — no options/strikes/IV needed at all for this signal,
since it only requires spot closes and the event calendar). Reuses
`_annualized_rv` from `scripts/validate_vol_spread_signal.py` directly.
Same 2024-01-01+ window (bhavcopy new-format cutover, for the same reason
as every prior signal — one data source, not cross-joined with a
separately-fetched series).

## Grouping — binary, not quintile

**Two groups: "event days" (as defined above) vs "non-event days"** —
not quintiles. With ~18 RBI dates + ~4 budget dates over the ~2.5-year
window, a ±1-day window yields roughly 60-70 event-days out of ~600
trading days (~10%) — too thin a sample to support 5 buckets
meaningfully, and the underlying question ("is proximity to a known event
different from an ordinary day") is inherently binary, not a continuous
score to rank.

**Primary comparison: RBI + Budget pooled** (the larger, more
statistically meaningful sample). **Secondary breakdown: RBI-only**
reported alongside for transparency (Budget alone is too thin, ~4 events,
to stand on its own) — both reported regardless of outcome, same
"report all cuts, not just the flattering one" discipline as every prior
doc in this line.

## Validation criterion

For each underlying (NIFTY, BankNifty), report: n and mean forward 20d
RV for event days vs non-event days (pooled RBI+Budget), and the same
split for RBI-only. **The signal works if event days show a materially
higher mean forward RV than non-event days** — no invented significance
test, same direct-arithmetic style as `docs/REGIME_VALIDATION.md` and
every prior report; read the gap against the (much smaller) event-day `n`
before over-interpreting it.

## Backtest window

2024-01-01 through the latest cached bhavcopy date (~2026-07-27), same
window as every other signal in this line, for direct comparability.

## What would make this validation untrustworthy after the fact

- Widening or narrowing the ±1-day event window after seeing a weak
  result.
- Adding NSE index rebalance or any other event type into the pool after
  seeing RBI+Budget alone underwhelm.
- Reporting only the RBI-only or only the pooled cut, whichever looks
  better.
- Connecting this to VRP's trade data or any strategy backtest before
  this validation's own verdict locks.
- Treating a positive result here as vindication of the closed
  vol-conditioning line — this is a structurally different signal (known
  calendar fact vs. inferred continuous statistic), and a pass here says
  nothing about whether IV-level, skew, or term structure were wrongly
  closed.

## Pass/fail bar

Not a P&L bar — a forward-outcome separation check, same category as
every prior vol/event signal in this project. **Pass: event days show a
materially higher mean forward RV than non-event days, on the pooled
RBI+Budget cut, with the RBI-only cut reported alongside as a
consistency check** (not required to independently pass — a much thinner
sample). A negative or flat result is as legitimate an outcome as a
positive one. If this fails too, the honest read is that this project has
now tested five independently-constructed vol/event signals (four
continuous, one discrete-calendar) without finding one that predicts NSE
index volatility — a much stronger basis for concluding no such signal is
findable in the available data than any single failure alone.
