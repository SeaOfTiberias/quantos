# IV-minus-RV Vol Spread — Methodology, Pre-Committed 2026-07-24 Before Any Result Exists

S8-1 (`docs/REGIME_VALIDATION.md`, 1254 real trading days) proved
`core/regime/classifier.py` does not reliably separate forward market
outcomes: RANGING isn't calmer than VOLATILE (0.83 vs 1.27 mean 20d
realized vol), TRENDING_BEAR precedes higher forward returns than
TRENDING_BULL, and VOLATILE precedes the *best* forward returns while the
system cuts size on it. Fable's 2026-07-24 design review (see memory
`quantos-regime-signal-redesign-plan`) confirmed the classifier's flaw is
structural, not a tuning problem: it scores India VIX as an absolute
**level** (LOW/ELEVATED/HIGH/EXTREME bands), never checking whether that
level was actually justified by what volatility did next. A spread between
implied and realized vol is different information — whether a premium is
being paid for risk that materializes, not just where VIX sits on a scale.

This doc fixes every design choice before any code runs, so nothing here
gets tuned after seeing a result — same discipline as
`docs/S8_3_MOMENTUM_METHODOLOGY.md` and `docs/VRP_METHODOLOGY.md`.

**Do not edit this file after the validation has run.** If a parameter
turns out wrong, that's a finding for a NEXT pre-registered run, not a
retroactive edit to this one.

**Mandatory sequencing (Fable-mandated):** this signal is validated here
fully, on its own terms, against real forward realized volatility. It is
NOT checked against VRP short strangle's trade data in this pass — doing
so before this validation completes would be exactly the "regime-filtered
subset as the headline" rescue-narrative `docs/VRP_METHODOLOGY.md` already
bans in writing. If a VRP-reconnection step happens, it is separate, later,
and explicitly flagged as its own thing — not part of this doc's result.

## IV source — resolved, not assumed

The original ask named two candidate sources: "India VIX" and "a real
NSE-computed 30-day NIFTY implied-vol index." **These are the same
instrument.** India VIX *is* NSE's 30-calendar-day-forward implied
volatility index, computed from the NIFTY Index Options order book
(CBOE-licensed methodology) — there is no separate NSE-published NIFTY IV
index distinct from it. No second data source exists to reconcile.

**Availability, verified rather than assumed:** `core/regime/fetcher.py`'s
`_fetch_vix` already pulls `VIX_SYMBOL = "INDIA VIX"` daily history from
the broker, and `scripts/validate_regime_classifier.py` already fetched
and used it successfully across the full 2021-06-28 to 2026-07-17 window
(1254 replayed days, `docs/REGIME_VALIDATION.md`) — the same symbol, same
broker, same historical-data endpoint this doc's harness reuses. That is a
real, already-proven fetch of the exact series this signal needs, not an
assumption. The new harness re-fetches independently (no cached reuse of
S8-1's run) and its own fetch step is the live re-verification: if the
pull comes back short or fails, the harness aborts and reports that,
rather than silently proceeding on stale trust.

**What "IV" means here:** the raw India VIX daily close, unmodified — it
is already expressed as an annualized volatility percentage (e.g. 14.5
means 14.5%/yr), so it is used directly, with no rescaling.

## Realized-vol construction

**Trailing RV window: 20 trading days**, close-to-close, of NIFTY 50 spot
(`NIFTY_SYMBOL = "NIFTY 50"`, same series `core/regime/fetcher.py` already
uses for trend). Computed as the population stdev of daily log returns
over the trailing 20 sessions, annualized (`stdev * sqrt(252) * 100`) to
put it on the same vol-point scale as India VIX.

**Why 20, not 10 (pre-registered choice, not tuned after seeing results):**
India VIX is explicitly a 30-*calendar*-day-forward measure. 20 trading
days is ~28 calendar days (with NSE's ~5-day week and holidays) — the
closer match of the two candidate windows the original ask offered to
VIX's own stated horizon. Using a mismatched window (e.g. 10 trading days
~= 14 calendar days) would compare IV's 30-day-forward number against a
realized-vol estimate covering less than half that horizon, which biases
the "was the premium earned" comparison before it starts. This is a
horizon-matching argument, decided now, before any bucket result exists.

**Forward RV window: also 20 trading days**, same construction, but over
the 20 sessions *after* the day being scored (`t+1` through `t+20`) — this
is the outcome the spread is trying to predict, not a feature. Using the
same window length as the trailing RV keeps "was IV over/under-priced"
directly comparable pre- and post-observation.

## Spread construction

**Spread_t = IV_t (India VIX close) − RV_trailing_20d_t**, a plain
difference in vol points. Chosen over a ratio (IV_t / RV_trailing_20d_t)
as the primary construction because it is the simpler, more auditable of
the two — same preference `docs/VRP_METHODOLOGY.md` already stated for
strangle-over-condor ("the simplest, most auditable read... fewest
researcher degrees of freedom"). A ratio variant may be reported
alongside as an informational cross-check but is never the headline
metric or the basis for the verdict.

No lookahead: Spread_t uses only IV_t (same-day VIX close — the live
system already treats same-day VIX as a contemporaneous input, not a
future one) and RV_trailing_20d_t (days `t-19` through `t`, all in the
past relative to `t`). The forward-RV outcome used to score the spread
(`t+1` through `t+20`) is deliberately in the future — it's the label
being predicted, not an input.

## Bucketing

**Quintiles of the spread distribution across the full replayed sample**
— data-driven cut points computed once the whole sample is replayed, not
hand-picked thresholds (avoids re-using the classifier's own mistake of
hand-picked VIX bands that were never checked against outcomes). Q1 =
lowest 20% of spread values (most negative — IV below trailing RV, "vol
underpriced" by this measure) through Q5 = highest 20% (IV most above
trailing RV, "vol richest").

## Validation criterion

For each quintile bucket:
- **Mean IV_t**, **mean forward RV_20d_t** (the actual realized vol over
  the next 20 sessions), and **mean earned premium = IV_t − forward
  RV_20d_t**.
- **% of days where the premium was actually earned** (IV_t > forward
  RV_20d_t) — the direct, walk-forward answer to "if you'd sold vol on
  this day because the spread looked rich, would realized vol have come
  in under what you were paid to bear."

**The signal works if Q5 (highest spread) shows a larger mean earned
premium and a higher earned-premium hit rate than Q1 (lowest/most negative
spread)** — i.e., days this spread flags as "richest" actually do precede
IV outrunning what materializes, more than days it flags as "cheapest" or
underpriced. The mirror check: Q1 should show a smaller (or negative)
earned premium — on those days, realized vol should come in closer to or
above what IV priced, since the spread said IV wasn't paying much of a
premium at all.

Report is a plain table (bucket, n, mean spread, mean IV, mean forward RV,
mean earned premium, % premium earned) plus a direct read of the gaps
between Q5 and Q1, in the same zero-invented-significance-test style as
`docs/REGIME_VALIDATION.md`. Sample sizes (`n`) are reported so the gaps
can be read against them, not asserted as significant.

## Replay mechanics

Walk-forward, no lookahead, mirroring `scripts/validate_regime_classifier.py`'s
structure and reusing its chunked/throttled/retried fetch layer
(`fetch_chunked_daily`) directly rather than reimplementing it. Unlike that
script, this signal needs no breadth universe (it uses only NIFTY spot and
India VIX) and no 260-day EMA/percentile warmup — the only requirement per
day is 20 trailing trading days of NIFTY closes, so replay starts at index
20 rather than 260, yielding a longer usable sample from the same fetch
window.

## Backtest window

Same 5-year default as `scripts/validate_regime_classifier.py`
(`--years 5`), fetched from the same broker via the same chunked daily
history calls — reusing an already-proven fetch pattern rather than
inventing a new one.

## Pass/fail bar

Not a P&L bar (this is not a strategy backtest, it's a forward-outcome
separation check — same kind of validation S8-1 was for the classifier,
not the `has_positive_edge` PF/Sharpe bar used for VRP/S8-3/S8-4). **Pass:
Q5's earned-premium hit rate AND mean earned premium both exceed Q1's, by
a margin that isn't trivially explained by the sample-size gap between
buckets.** No p-value or invented significance test is computed — the
report presents the numbers and reads the gap, matching this project's
established style (`docs/REGIME_VALIDATION.md`, `docs/EXPECTANCY_CHECK.md`).
A negative result (no separation, or the wrong-direction separation like
S8-1 found for RANGING vs VOLATILE) is as legitimate an outcome as a
positive one.

## What would make this validation untrustworthy after the fact

- Changing the RV window, the spread construction (difference vs ratio),
  or the bucketing method after seeing a weak or strong result.
- Switching to a hand-picked threshold instead of quintiles because
  quintiles didn't show separation.
- Checking this signal against VRP's trade data before this validation's
  own verdict is locked — the exact rescue-narrative sequencing Fable's
  review flagged as the one rule that matters most here.
- Reporting only the buckets that happen to separate well while omitting
  the middle ones from the table.

If any of the above turns out to matter, it becomes a new, separately
pre-registered run — not a retroactive edit here.
