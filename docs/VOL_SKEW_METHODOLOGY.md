# NIFTY Option Skew — Methodology, Pre-Committed 2026-07-25 Before Any Result Exists

## Why this exists

Vol-conditioning has failed twice in this project on its own pre-registered
terms: `core/regime/classifier.py`'s VIX-level bands (S8-1,
`docs/REGIME_VALIDATION.md`, 1254 real days — RANGING wasn't calmer than
VOLATILE, TRENDING_BEAR preceded higher forward returns than TRENDING_BULL),
and the IV-minus-realized-vol spread built to replace it
(`docs/VOL_SPREAD_METHODOLOGY.md` / `docs/VOL_SPREAD_VALIDATION.md`, 1228
real days — non-monotonic, wrong-direction at the endpoints, Fable-confirmed
clean/structural failure). Fable's close-out on the second failure was
explicit: no third attempt without a genuinely new data source — real
options-implied term structure or skew, not another cut of
VIX-close-vs-spot-close (see memory `quantos_regime_signal_redesign_plan`).

**This doc pre-registers that third attempt: NIFTY option skew** — the gap
between OTM put implied vol and OTM call implied vol, computed from real
per-strike settlement prices, not from India VIX at all. Both prior
attempts used a single number (VIX's own level, or VIX minus realized vol).
This is structurally different information: it asks whether the market is
pricing downside moves richer than upside moves on a given day, which VIX
alone cannot express since VIX is a single at-the-money-ish blended number
across the whole chain.

Term structure (front-month vs back-month ATM IV) is the other candidate
Fable named. It is deliberately NOT built in this pass — one variable at a
time, same discipline as the turnover ablation's quarterly-only cadence
choice and the vol-spread doc's difference-not-ratio choice. If skew fails
cleanly, term structure is the natural next candidate, pre-registered
separately.

**Do not edit this file after the validation has run.** A wrong parameter
is a finding for a NEXT pre-registered run, not a retroactive edit here.

**Mandatory sequencing (same rule as `docs/VOL_SPREAD_METHODOLOGY.md`,
restated because it's the one that matters most):** this signal is
validated fully, on its own terms, against real forward realized
volatility. It is NOT checked against VRP short strangle's already-failed
trade data (`docs/VRP_BACKTEST_RESULTS.md`, PF 1.034/Sharpe 0.092) or the
Iron-Condor-mislabeled-as-straddle CSV reviewed 2026-07-25 in this pass —
doing so before this validation's own verdict is locked would be the same
"regime-filtered subset as the headline" rescue-narrative
`docs/VRP_METHODOLOGY.md` already bans in writing. Any reconnection step is
separate, later, and explicitly flagged as its own thing.

## Data source — resolved, not assumed

**`core/options/vrp/bhavcopy.py`'s already-cached parsed bhavcopy files**
(`data_cache/nse_bhavcopy/parsed/*.csv`), built for VRP. Verified directly
before writing this doc, not assumed:

- 737 trading days already cached locally, `20230724.csv` through
  `20260722.csv`.
- Checked `20260722.csv` directly: 1584 rows, **one `underlying_close`
  value shared across every row that day** (23996.25) — confirmed, not
  assumed, so it's usable as that day's NIFTY spot without a separate
  broker fetch. 18 expiries present that day (weeklies through the nearest
  few months, monthlies further out), 105 strikes for the nearest expiry
  alone, ₹50 strike spacing — dense enough to find a strike close to any
  target moneyness.
- `underlying_close` is **only populated in the new bhavcopy format**
  (`bhavcopy.py`'s own docstring, `CUTOVER_DATE = 2024-01-01`). Legacy-format
  days (2023-07-24 through 2023-12-31, already cached) have no
  underlying_close and are **excluded from this validation** rather than
  cross-joined against a separately-fetched NIFTY series — one data source,
  not two stitched together. This shortens the usable window to
  **2024-01-01 through the latest cached date (~2026-07-22, ~2.5 years)** —
  shorter than the 5-year window `docs/VOL_SPREAD_VALIDATION.md` used. That
  is a real limitation of this pass, stated up front, not discovered after
  a weak result.
- **A working Black-Scholes IV solver already exists**:
  `core/options/greeks.py::implied_volatility()` (bisection, not Newton —
  already chosen for stability near expiry/deep ITM-OTM, per its own
  docstring). Reused as-is, not reimplemented.
- **This validation needs no live broker connection at all** — every input
  (spot, strikes, settlement prices, expiries) comes from the already-cached
  bhavcopy files. Unlike `docs/VOL_SPREAD_VALIDATION.md`'s run, which
  blocked on an expired Fyers token requiring interactive OAuth
  (`feedback_interactive_scripts`), this backtest has no such dependency —
  worth confirming stays true when the harness is actually built, since it
  removes a real recurring friction point.

## Expiry selection

For each trade date, the **nearest listed expiry with at least 3 calendar
days remaining** (`expiry − trade_date >= 3`). Skips 0–2 DTE to avoid
expiry-day pin/gamma distortion in the IV solve, without reaching past the
nearest genuinely tradeable weekly. Deterministic given the date — no
judgment call at replay time.

## Strike selection — OTM put and OTM call

**Target moneyness: 5% OTM each side** — put strike target = spot ×
0.95, call strike target = spot × 1.05. Pre-registered as a fixed number,
not tuned after seeing results; 5% is the common convention for a
"crash-insurance" skew read on NIFTY-sized underlyings.

**Selection rule:** for the day's chosen expiry, take the strike **nearest**
to each target (ties broken toward the strike further OTM, so the rule
is deterministic). **Skip the day** (excluded from the sample, count
reported) if the nearest available strike's actual moneyness is more than
2 percentage points from its 5% target (i.e., outside 3%–7% OTM) — guards
against thin/sparse strike listings (e.g., early days of a new far-dated
series), not routine ₹50-increment rounding, which at NIFTY's ~24,000
level is ~0.2% of spot and will almost never trip this.

## IV computation

`implied_volatility(market_price=settle_price, spot=underlying_close,
strike=<selected strike>, days_to_expiry=(expiry − trade_date).days,
option_type=PUT|CALL, risk_free_rate=core.options.greeks.DEFAULT_RISK_FREE_RATE)`
— settlement price used as `market_price` (NSE's official daily
theoretical/traded settlement, same price basis VRP's own methodology
already relies on for this data; not a new caveat introduced here).

**Fallback-contamination guard:** `implied_volatility()` silently returns a
default 0.18 when `days_to_expiry <= 0`, `market_price <= 0`, or
`market_price` is at/below intrinsic value — real fallback conditions, not
solver failures, but a constant 0.18 mixed silently into the sample would
contaminate the skew calculation without any visible signal. This
validation checks those same preconditions itself **before** calling the
solver and **skips the day** (both legs) if either the put or call leg
would hit the fallback path, rather than trusting the return value alone.
Skip count reported alongside the moneyness-tolerance skip count.

## Skew construction

**Skew_t = IV_put_OTM,t − IV_call_OTM,t**, a plain difference in vol
points — same difference-not-ratio precedent `docs/VOL_SPREAD_METHODOLOGY.md`
already set (simpler, more auditable, fewer researcher degrees of freedom,
per `docs/VRP_METHODOLOGY.md`'s stated preference). Positive skew = puts
pricing richer than calls (the usual equity-index pattern — downside
insurance bid up). A ratio variant may be reported alongside as an
informational cross-check but is never the headline metric.

No lookahead: every input (spot, strikes, settlement prices) is dated `t`
itself, same-day, nothing from `t+1` onward.

## Realized-vol construction (the forward outcome being predicted)

Reuses `docs/VOL_SPREAD_METHODOLOGY.md`'s exact construction, so the two
signals are read on the same scale and directly comparable:

- **Trailing RV, 20 trading days**, close-to-close, computed from the same
  bhavcopy `underlying_close` series (population stdev of daily log
  returns, annualized via `× sqrt(252) × 100`) — reported alongside the
  skew for context, not used as a second predictor in this pass.
- **Forward RV, 20 trading days** (`t+1` through `t+20`), same
  construction — the label being predicted.

## Bucketing

**Quintiles of the skew distribution across the full replayed sample** —
data-driven cut points computed once over the whole sample, not
hand-picked thresholds. Q1 = most negative/lowest skew (calls pricing
richer than puts, or puts least rich), Q5 = highest skew (puts richest
relative to calls).

## Validation criterion

For each quintile bucket: n, mean skew, mean forward RV_20d, and — mirroring
`docs/VOL_SPREAD_VALIDATION.md`'s table exactly — mean forward RV compared
across buckets.

**The signal works if forward realized vol is monotonically higher moving
from Q1 to Q5** — i.e., days the market prices with the richest put skew
are genuinely followed by higher realized volatility than days with flat
or inverted skew, which is the textbook claim about skew as a fear gauge.
A non-monotonic or flat result (the same failure shape both prior attempts
showed) is a clean fail, not grounds for a bucket-count or window tweak.

Report is a plain table plus a direct read of the Q5-vs-Q1 gap, same
zero-invented-significance-test style as `docs/REGIME_VALIDATION.md` and
`docs/VOL_SPREAD_VALIDATION.md`. Sample sizes reported so gaps can be read
against them, not asserted as significant.

## Backtest window

**2024-01-01 through the latest cached bhavcopy date** (~2026-07-22 as of
this writing; the harness re-checks the actual latest cached file at run
time rather than hardcoding a date). ~2.5 years, ~625 trading days before
any skip-rule exclusions — shorter than the 5-year VIX-based window, a
real constraint of using per-strike settlement data instead of a single
index series, stated here rather than after a weak result.

## What would make this validation untrustworthy after the fact

- Changing the 5% OTM target, the moneyness-tolerance band, the minimum
  DTE, or the skew construction (difference vs ratio) after seeing a weak
  or strong result.
- Widening the window by cross-joining legacy-format bhavcopy days against
  a separately-fetched NIFTY series to recover more history — that's a
  different, separately pre-registered construction, not a patch to this
  one.
- Checking this signal against VRP's trade data, or the Iron-Condor-CSV
  straddle reviewed 2026-07-25, before this validation's own verdict is
  locked.
- Building term structure in the same pass and reporting whichever of the
  two looks better.
- Reporting only the buckets that separate well while omitting the middle
  ones.

## Pass/fail bar

Not a P&L bar — a forward-outcome separation check, same category as S8-1
and the vol-spread validation, not the `has_positive_edge` PF/Sharpe bar
used for strategy backtests. **Pass: forward RV is monotonically higher
Q1→Q5, with a Q5-vs-Q1 gap that isn't trivially explained by the
sample-size split between buckets.** No p-value or invented significance
test. A negative result (flat, non-monotonic, or wrong-direction — the
same shape both prior vol-conditioning attempts produced) is as legitimate
an outcome as a positive one, and closes this thread the same way PEAD and
the vol-spread signal closed: no term-structure follow-up without a real
reason to expect it'd behave differently.
