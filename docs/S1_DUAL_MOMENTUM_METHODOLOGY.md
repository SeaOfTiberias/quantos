# Regime-Filtered Dual-Momentum — Methodology, Pre-Committed 2026-07-24 Before Any Result Exists

The user brought this as one of three fully-specified strategy proposals
this session (see memory `quantos-three-strategy-proposals-review`). Of
the three, Strategy 3 (an earnings-beat breakout) was rejected outright —
it's PEAD's already-shelved anomaly with a new execution layer bolted on
— and Strategy 2 (Alpha-50 mean-reversion) was built, tested, and shelved
as inconclusive-negative after a Fable review caught a real measurement
bug. This is Strategy 1, the only one of the three not yet tested.

**Known overlap with prior failures, stated up front, not hidden:** the
regime filter here (Nifty 50 vs its own EMA200) is a simpler cousin of
two regime-conditioning signals that have both already failed their own
validation in this project — the VIX-level classifier (S8-1) and an
IV-minus-realized-vol spread (closed the same day as this doc). The
momentum core (rank by return, rotate into the top names) was already
tested once as S8-3 and, after a survivorship-bias fix, lost to both
benchmarks (-15.6pt vs Nifty 500, -64.6pt vs Nifty Alpha 50). This is not
a literal re-run of either — different universe, different ranking
formula, different exit mechanics (ATR-based stops neither prior test
used) — but it inherits real risk from both lineages. Per this project's
now-established convention (S8-3, S8-4), **the regime filter is treated
as informational-only, not a hard gate on the headline result.**

This doc fixes every design choice before `core/rotation/dual_momentum.py`
or its backtest driver are run, so nothing here gets tuned after seeing a
result — same discipline as every prior methodology doc in this project.

**Do not edit this file after the backtest has run.** If a parameter
turns out wrong, that's a finding for a NEXT pre-registered run, not a
retroactive edit to this one.

## Why a new module, not an extension of `core/rotation/equity_curve.py`

`core/rotation/ranker.py`'s docstring is explicit: *"Do not tune TOP_N,
LOOKBACK_DAYS, or the ranking formula... there is exactly one ranking
function [so] live execution can never silently drift from what was
actually backtested."* `core/rotation/executor.py` (S8-3's live rotation
path) imports directly from it. Modifying `ranker.py` or
`equity_curve.py` in place to fit a completely different ranking formula,
trend filter, and exit mechanic would risk destabilizing that
live-critical code path for an unrelated one-off test. Per this
project's established pattern when a new signal needs different
mechanics (e.g. `fetch_chunked_hourly` copied `fetch_chunked_daily`'s
structure rather than parameterizing it), this strategy gets its own
module, copying the well-tested day-by-day mark-to-market loop structure
from `equity_curve.py` but built around its own ranking/filter/exit
logic.

## Filter 1 — Trend (own stock)

**EMA50 > EMA200 on the stock's own daily closes.** A stock is eligible
for ranking on a given rebalance date only if this holds as of the last
completed daily bar. Reuses the existing walk-forward EMA pattern
(`core.regime.fetcher._ema`, called day-by-day on a trailing slice — the
same pattern `core/meanreversion/gutcheck.py`'s `walk_forward_emas` and
`scripts/validate_regime_classifier.py`'s replay both already use) rather
than a new EMA implementation.

## Filter 2 — Composite momentum score

**Score = 0.5 × Return_90d + 0.5 × Return_180d**, where Return_Nd =
`close_t / close_{t-N} - 1`, N counted in TRADING days (not calendar
days) — consistent with S8-3's own convention (`LOOKBACK_DAYS = 252`
trading days for its 52-week window) and this project's general practice
of trading-day-denominated lookbacks throughout. A symbol needs ≥180
trading days of history to be scoreable at all (same "warm up before
ranking" discipline S8-3 used for its 252-day requirement, just scaled to
this strategy's own shorter lookback).

## Filter 3 — Regime (informational only, not a hard gate)

**Nifty 50 (the index itself, not Nifty 200) above its own EMA200.**
Reported as a regime-split variant on the same unfiltered trade set — per
S8-1's finding (this classifier-adjacent signal has a 0-for-2 record in
this project) and S8-3/S8-4's resulting convention, **this is never the
basis for the go/no-go verdict.** The unfiltered result is the headline;
the regime split is informational only, shown to see if it's directionally
useful even though it isn't trusted as a hard gate.

## Selection & rebalance

**Top 15 by composite score among Filter-1-passing stocks, weekly
rebalance.** Rebalance/ranking date = the last NIFTY trading day of each
ISO calendar week (Mon-Sun) — same anchor S8-3 used, for the same reason
(a common calendar every symbol rebalances against). **Entries fill at
the NEXT trading day's OPEN** (typically Monday, holiday-adjusted) — this
is a deliberate, more realistic departure from S8-3's own convention
(which filled entries at the rebalance day's own close): the strategy
spec explicitly says "market order at Monday open," and a next-session
open fill is also the same no-lookahead convention this session's
mean-reversion gut-check used for its daily-baseline path
(`core/meanreversion/gutcheck.py`'s `forward_returns`).

**Exit band is asymmetric, exactly as specified — top 15 to enter, top 25
to stay.** A position exits on rank-dropout only if it falls out of the
top 25 at a WEEKLY re-rank (checked at rebalance dates only, matching
S8-3's own weekly-only rank-dropout cadence) — this is a real,
intentional anti-chattering buffer, unlike S8-3 which deliberately had
none. Pre-committed as specified, not tuned.

## Exit mechanics — initial stop + Chandelier trail

**ATR14**: Wilder's Average True Range, standard definition (true range =
`max(high-low, |high-prev_close|, |low-prev_close|)`, 14-period Wilder
smoothing — same smoothing convention as this session's `rsi14` in
`core/meanreversion/gutcheck.py`, just applied to true range instead of
gain/loss).

**Initial stop** = `entry_price - 2.5 × ATR14` (ATR as of the last
completed daily bar before entry — no lookahead).

**Chandelier trail** = `highest_high_since_entry - 2 × ATR14` (ATR
recomputed daily as new bars close — standard Chandelier convention, not
frozen at entry).

**Combined stop level, a pre-registered interpretation the spec doesn't
state explicitly but requires to make "initial stop" and "trailing
stop" coexist sensibly**: `stop_level = max(initial_stop, chandelier_line)`
— a stop that only ever ratchets up, never loosens. At entry,
`highest_high_since_entry = entry_price`, so the Chandelier line starts
at `entry_price - 2×ATR`, tighter than the 2.5×ATR initial stop — the
initial stop governs until the position has moved favorably enough for
the Chandelier line to overtake it.

**A real, discovered mathematical property of these exact multipliers,
disclosed here before any backtest ran (found while unit-testing the
combination logic, not while looking at results)**: since 2.0 < 2.5, the
Chandelier line is mathematically at or above (tighter than) the initial
stop from the moment of entry onward, given `highest_high_since_entry`
starts at `entry_price` — the initial stop only actually binds when ATR
expands more than 25% right after entry with no favorable price move yet.
In practice this means the Chandelier line is the operative stop almost
all the time; the initial stop functions as a volatility-expansion
backstop, not a day-to-day governor. This is a property of the spec's own
chosen multipliers (2.5 vs 2.0), not a modeling choice made after seeing
results.

**Trigger convention**: checked against the daily CLOSE, not an intrabar
low — the position exits if that day's close is at or below the current
stop level, and the exit fills at that close. Chosen for the same reason
VRP chose a strangle over a condor: the simplest, most auditable
construction, with the fewest researcher degrees of freedom. An
intrabar/stop-loss-order variant is legitimate future work if this
candidate survives, not part of this pass.

**Exit priority when both trigger the same day**: the stop-loss check
runs on EVERY trading day (mirroring `equity_curve.py`'s existing
"stop_loss"/"ema_cross" variants, which are also checked daily, not just
at rebalance); the rank-dropout check only runs on rebalance days. If
both would trigger on the same rebalance day, the stop-loss exit is
recorded (it's the more specific, price-driven reason) — this can only
happen on a rebalance day, and is expected to be rare.

**3 years**, matching S8-3's own default, for direct comparability.

## Pass/fail bar

**Same bar used throughout this project:** `core/backtest/parser.py`'s
`has_positive_edge` convention — profit factor > 1.0 AND Sharpe > 0.5 —
computed on the capital-tracked equity curve (`core/rotation/equity_curve.py`'s
CAGR/Sharpe/max-drawdown methodology, reused for consistency with S8-3's
own capital-tracked run), on the UNFILTERED (no regime gate) result.

## What would make this backtest untrustworthy after the fact

- Changing the 0.5/0.5 score weighting, the 90d/180d windows, the 15/25
  entry-exit band, or the 2.5×/2× ATR multipliers after seeing a weak or
  strong result.
- Reporting the regime-filtered variant as the headline instead of
  unfiltered — same rule S8-1's finding already established for S8-3/S8-4.
- Switching the stop trigger from close-based to intrabar after seeing
  the close-based version look worse.
- Skipping the point-in-time universe fix if this candidate looks
  positive and quietly treating the survivorship-biased number as final
  (S8-3's own history is the direct cautionary example here).

If any of the above turns out to matter, it becomes a new, separately
pre-registered run — not a retroactive edit here.
