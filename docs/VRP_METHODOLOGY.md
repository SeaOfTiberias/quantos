# Options VRP (Variance Risk Premium) Backtest — Methodology, Pre-Committed 2026-07-23 Before Any Result Exists

Fable's 2026-07-19 review flagged VRP as "the genuinely best-supported edge"
among remaining candidates after Darvas (S7-3, dead) and S8-3 RS momentum
rotation (corrected to a -15.6pt/-64.6pt loss vs benchmarks) — but flagged
`core/options/backtester.py` as the wrong tool, since it's expiry-only
Black-Scholes and can't see the path risk that actually kills short-vol
strategies. This doc fixes every strategy-design choice before any P&L
simulator code is written, so nothing here gets tuned after seeing a
result — same discipline as `docs/S8_3_MOMENTUM_METHODOLOGY.md`.

**Do not edit this file after the backtest has run.** If a parameter turns
out wrong, that's a finding for a NEXT pre-registered run, not a
retroactive edit to this one.

## Data (Phase 1 — already built and run, 2026-07-23)

`core/options/vrp/bhavcopy.py` + `scripts/fetch_vrp_bhavcopy.py`. NSE daily
F&O bhavcopy, both archive generations, filtered to NIFTY index options,
cached locally in `data_cache/nse_bhavcopy/` (gitignored — see that
module's docstring). **Window: 2023-07-24 to 2026-07-22, 737 trading days,
1,182,046 NIFTY option rows.** Spans both a monetary-shock vol event
(2024-06-04 election-result crash) and a geopolitical one (2025-04
Pahalgam/Sindoor), so the sample isn't calm-markets-only — the whole VRP
thesis is about the gap between implied and realized vol, which only shows
up if realized vol actually moves.

## Structure

**Short strangle: sell one OTM call + one OTM put, same expiry, opened and
closed together.** Chosen over a short straddle (max premium, but the
largest gamma/tail exposure of the three candidates considered) and an
iron condor (defined-risk, but the long wings dilute the very IV-RV gap
being measured — makes "no edge" and "edge eaten by wing cost" impossible
to tell apart). No delta-hedging, no adjustment mid-trade — a raw read of
the premium, not a hedged-vol-trading strategy.

## Underlying and expiry cycle

**NIFTY weekly options.** "Weekly" is defined data-driven, not by a
hardcoded expiry day-of-week: on each entry date, the target contract is
whichever unexpired NIFTY expiry present in that day's bhavcopy is
soonest. NSE has changed NIFTY's designated weekly-expiry weekday more
than once within this backtest's own window (last changed to Tuesday, per
NSE's 2025-07 circular) — hardcoding a day-of-week would silently misfire
across that change; deriving it from the data each cycle does not.

## Entry rule

**Roll immediately: enter a new cycle the trading day immediately after
the prior cycle's expiry/settlement**, selling the next-nearest unexpired
weekly contract at that point. This produces one entry every trading week
with no engineered gaps, and lands naturally in a ~5-7 calendar-day DTE
band under NIFTY's actual (holiday-adjusted) weekly cadence — DTE is a
consequence of this rule, not a filter applied on top of it. The very
first cycle of the backtest enters on the first trading day of the window
(2023-07-24) against whatever weekly contract was nearest that day.

## Strike selection

**~0.20-delta short strikes, computed from that day's own priced
options**, using `core/options/greeks.py`'s existing Black-Scholes delta
(the same machinery `core/options/backtester.py` already uses for its
`find_strike_for_delta` binary search) with IV backed out of the real
settle price at each candidate strike, not an assumed constant IV. If
delta cannot be computed for a given day (e.g. degenerate/zero IV solves,
which the backtest run must log and count, not silently skip past),
**fall back to a fixed distance of 2% OTM from the underlying close** —
pre-committed now so the fallback is never chosen after seeing which one
looks better.

## Exit rule

**Hold to expiry, cash-settle. No early close, no stop-loss, no profit
target, no rolling.** This is the simplest, most auditable read of the
IV-RV gap and has the fewest researcher degrees of freedom — every open
question about "when do you take profit" or "when do you cut losses" is a
tunable parameter, and this backtest is deliberately choosing to have
none of those for its first pass. A managed-exit variant (profit target /
stop) is legitimate future work, but only as a SEPARATELY pre-registered
run against this one's own result, not a retroactive change to it.

## What Phase 3 must still resolve (not decided here — implementation
## details, not strategy-design choices, but flagged now so they can't be
## quietly tuned once results exist)

- **Lot size.** The new-format bhavcopy carries `NewBrdLotQty` directly
  (e.g. 50 in a 2024-01-01 sample row) — real, per-contract, per-date data,
  not a guess. The legacy schema (pre-2024-07-08) has no lot-size column;
  NIFTY's contract lot size has changed more than once inside this
  backtest's window (SEBI's 2024 minimum-contract-size rules). Phase 3
  needs either a small hand-built point-in-time lot-size table (same
  pattern as `core/rotation/nifty500_reconstitution.py`'s press-release
  table) or another NSE source that carries it for legacy dates — this
  must be sourced from real records, not assumed constant across the
  window the way S8-4's `LOT_SIZE = 65` was only safe to assume because
  it checked against real tradebook fills first.
- **P&L scope.** First pass reports pooled per-trade statistics (profit
  factor, Sharpe, win rate — the same headline metrics S7-3/S8-3/S8-4 all
  led with), NOT a real-capital equity curve. A capital-tracked run (like
  `core/rotation/equity_curve.py` was for S8-3, built only after the
  pooled-stats version existed) is legitimate follow-on work, not part of
  this pre-registration.
- **Cost model.** `scripts/backtest_nifty_ema_options.py`'s
  `OPTIONS_COST_MODEL` (options-parameterized `CostModel` — STT on sell
  premium, F&O exchange rate) is the starting point, not
  `core/risk/costs.py`'s equity-intraday defaults. Margin/collateral cost
  of carrying a short strangle is a real cost this doesn't yet capture and
  needs its own decision before Phase 4.

## Pass/fail bar

**Same bar used throughout this project:** profit factor > 1.0 AND
Sharpe > 0.5 on the unfiltered, full-sample result (`core/backtest/parser.py`'s
`BacktestMetrics.has_positive_edge` convention, matching S8-3/S8-4).

## What would make this backtest untrustworthy after the fact

- Changing the strike delta, the entry-roll rule, or the exit rule after
  seeing a weak or strong result.
- Switching to a straddle or iron condor after seeing the strangle's
  number, without registering that as a new, separate run.
- Adding a stop-loss or profit-target rule only after seeing the raw
  hold-to-expiry result looks bad.
- Reporting a regime-filtered or vol-event-excluded subset as the
  headline instead of the full unfiltered sample.

If any of the above turns out to matter, it becomes a new, separately
pre-registered run — not a retroactive edit here.
