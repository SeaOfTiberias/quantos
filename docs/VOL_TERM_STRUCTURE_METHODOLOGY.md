# NIFTY + BankNifty ATM IV Term Structure — Methodology, Pre-Committed 2026-07-27 Before Any Result Exists

## Why this exists

Vol-conditioning has failed three times in this project on its own
pre-registered terms: `core/regime/classifier.py`'s VIX-level bands (S8-1,
`docs/REGIME_VALIDATION.md`), the IV-minus-realized-vol spread
(`docs/VOL_SPREAD_METHODOLOGY.md`), and NIFTY+BankNifty option skew
(`docs/VOL_SKEW_METHODOLOGY.md` + its BankNifty addendum). Fable's
2026-07-27 review of the skew result closed vol-conditioning at 3-for-3 and
was explicit: the one remaining genuinely different data source — **term
structure, front-month vs back-month ATM IV** — was named back on
2026-07-25 and never built (see memory `quantos_regime_signal_redesign_plan`).

**This doc pre-registers that 4th attempt.** All three prior signals used
either a single index-level number (VIX level, VIX-minus-RV) or a
single-expiry cross-sectional read (skew, within one expiry's chain). Term
structure is different in kind: it reads the **shape of the curve across
expiries** — whether near-dated uncertainty is priced richer or cheaper
than longer-dated uncertainty — which none of the three prior attempts
measured at all.

**Built for NIFTY and BankNifty together from the start**, not staged.
This is deliberately different from VRP's premium-selling strategy, which
had to shrink to NIFTY-only because BankNifty's monthly-only expiry cycle
(NSE discontinued its weekly cycle) broke VRP's weekly-roll cadence
assumption outright (`quantos_regime_signal_redesign_plan`). Term
structure has no such dependency — it only needs **two** sequential listed
expiries per underlying per day, which both NIFTY (weekly + monthlies) and
BankNifty (monthly-only) always have. Verified directly (not assumed)
before writing this: the already-cached raw bhavcopy zips
(`data_cache/nse_bhavcopy/raw/`) list every live expiry simultaneously for
both underlyings on every day, per `docs/VOL_SKEW_METHODOLOGY.md`'s own
"18 expiries present" check on NIFTY and the BankNifty addendum's "monthly
spacing, `2026-07-28, 2026-08-25, 2026-09-29, ...`" check — both have
≥2 live expiries on essentially every trading day.

**Do not edit this file after the validation has run.** A wrong parameter
is a finding for a NEXT pre-registered run, not a retroactive edit here.

**Mandatory sequencing (same rule as every prior vol-conditioning doc,
restated because it's the one that matters most):** this signal is
validated fully, on its own terms, against real forward realized
volatility. It is NOT checked against VRP short strangle's already-failed
trade data or the Iron-Condor-mislabeled straddle CSV before this
validation's own verdict is locked — same `docs/VRP_METHODOLOGY.md` ban on
reporting a rescued subset as the headline. Any reconnection step is
separate, later, and explicitly flagged as its own thing.

## Data source — resolved, not assumed

Same already-cached raw bhavcopy zips VOL_SKEW used
(`core/options/vrp/bhavcopy.py`'s `fetch_raw()`, `data_cache/nse_bhavcopy/raw/`),
re-parsed with the **same underlying-filtered parser already built**
(`scripts/validate_vol_skew_signal.py`'s `parse_raw_zip_for_underlying` /
`OptionRow`) — reused directly, not reimplemented, for both NIFTY and
BankNifty. Same 2024-01-01+ window as VOL_SKEW (`underlying_close` is only
populated in the new bhavcopy format; legacy days excluded, not
cross-joined against a separately-fetched spot series — one data source,
not two stitched together). No live broker connection needed.

## Expiry-pair selection

For each trade date: take every expiry listed that day with **at least 3
calendar days to trade date** (same `MIN_DTE = 3` as VOL_SKEW, same
pin/gamma-noise rationale), sort ascending by expiry date.

- **Front-month = the nearest qualifying expiry.**
- **Back-month = the next qualifying expiry after front-month.**

**Skip the day** (excluded from sample, count reported) if fewer than 2
qualifying expiries are listed.

**Disclosed asymmetry, not smoothed over:** NIFTY currently has weekly
expiries, so its front/back gap is typically ~1 week. BankNifty trades
monthly-only, so its front/back gap is typically ~1 month. This means
NIFTY's and BankNifty's term-structure readings measure the curve's slope
over structurally different horizons — a real difference between the two
runs, reported as such. The alternative (forcing a matched-DTE structure
via cross-expiry interpolation) would add model risk of its own and is
explicitly rejected here in favor of each underlying's own real, as-listed
expiry calendar — same "no live pathway warps to fit a preference" spirit
as the rest of this project's methodology docs.

## Strike selection — ATM, both legs

For **each** of the front-month and back-month expiries independently:
take the strike **nearest to that day's spot** (`underlying_close`,
confirmed shared across every row that day per VOL_SKEW's own check).

**Moneyness tolerance:** skip the day (both expiries) if the nearest
available strike is more than **1.5% away from spot** on either expiry —
a generous safety margin given NIFTY's ₹50 / BankNifty's ₹100 strike
spacing (each roughly 0.1–0.2% of spot at current levels), guarding
against thin/sparse strike listings rather than routine rounding.

## IV computation

`implied_volatility()` (`core/options/greeks.py`, same bisection solver
every prior signal used), called separately for the ATM call and the ATM
put at each expiry, using that leg's settlement price as `market_price`.

**ATM_IV for one expiry = mean(call IV, put IV)** at that expiry's chosen
strike — the standard "ATM straddle IV" convention (call and put IV
should be close via put-call parity at true ATM; averaging both is more
robust than picking one arbitrarily).

**Fallback-contamination guard, same as VOL_SKEW:** `implied_volatility()`
silently returns a default 0.18 when `days_to_expiry <= 0`, `market_price
<= 0`, or price is at/below intrinsic. This validation checks those same
preconditions itself before calling the solver and **skips the day**
(entirely — both expiries, both legs) if ANY of the four legs (front
call/put, back call/put) would hit the fallback path, rather than
trusting the return value. Skip count reported.

## Term structure construction

**Spread_t = ATM_IV_front,t − ATM_IV_back,t**, a plain difference (same
difference-not-ratio precedent as every prior signal in this line).

- **Positive spread (front pricier) = backwardation** — near-term
  uncertainty priced richer than longer-term, the textbook "stress/event"
  shape (real-world analogue: VIX futures curve inverting ahead of a
  known risk event).
- **Negative spread (front cheaper) = contango** — the normal,
  upward-sloping curve, the textbook "calm" shape.

No lookahead: every input (spot, strikes, settlement prices, both
expiries) is dated `t` itself.

## Realized-vol construction (the forward outcome being predicted)

Identical to every prior signal in this line, for direct comparability:
20 trading days, close-to-close, annualized (`× sqrt(252) × 100`),
computed from the same bhavcopy `underlying_close` series. Trailing RV
reported for context; forward RV (`t+1` through `t+20`) is the label being
predicted. Reuses `_annualized_rv` from `scripts/validate_vol_spread_signal.py`
directly.

## Bucketing

**Quintiles of the Spread_t distribution across the full replayed
sample** — data-driven cut points, not hand-picked thresholds. Q1 = most
negative spread (deepest contango), Q5 = most positive spread (deepest
backwardation). Reuses `quintile_cutoffs` / `assign_bucket` directly.

## Validation criterion

For each quintile: n, mean spread, mean forward RV_20d — same table shape
as every prior vol-conditioning doc in this project.

**The signal works if forward realized vol is monotonically higher moving
from Q1 (deepest contango) to Q5 (deepest backwardation)** — i.e.,
backwardation days are genuinely followed by higher realized volatility
than contango days, the textbook claim about term-structure inversion as
a stress signal. A non-monotonic, flat, or wrong-direction result (the
same failure shape all three prior attempts showed) is a clean fail, not
grounds for a bucket-count, DTE, or strike-tolerance tweak.

**NIFTY and BankNifty are run through the identical harness independently
and reported as two separate quintile tables with two separate pass/fail
verdicts** — never pooled, and the headline is never "whichever one
separated better" (same rule as the skew BankNifty addendum).

Report is a plain table plus a direct read of the Q5-vs-Q1 gap, zero
invented significance test, same style as every prior report in this
line.

## Backtest window

**2024-01-01 through the latest cached bhavcopy date** (harness re-checks
the actual latest cached file at run time rather than hardcoding a date).
Same window as VOL_SKEW, for direct comparability.

## What would make this validation untrustworthy after the fact

- Changing `MIN_DTE`, the 1.5% moneyness tolerance, or the spread
  construction (difference vs ratio) after seeing a weak or strong result.
- Forcing a matched-DTE structure across the two underlyings after seeing
  the disclosed asymmetry produce a weak result on one of them.
- Checking this signal against VRP's trade data or the straddle CSV before
  this validation's own verdict is locked.
- Reporting only whichever underlying (or which of the four vol-signal
  attempts overall) separates best.
- Adding a 3rd or 4th expiry point ("full curve slope," matching the
  post-hoc "smile magnitude" idea Fable already rejected for skew) if this
  2-point spread fails — that would be the same post-hoc-pattern trap
  Fable's 07-27 review flagged, not a genuinely new hypothesis.

## Pass/fail bar

Not a P&L bar — a forward-outcome separation check, same category as
every prior vol-conditioning validation, not the `has_positive_edge`
PF/Sharpe bar used for strategy backtests. **Pass: forward RV is
monotonically higher Q1→Q5, with a Q5-vs-Q1 gap that isn't trivially
explained by the sample-size split between buckets.** No p-value or
invented significance test. A negative result is as legitimate an outcome
as a positive one and would make this a clean 4-for-4 vol-conditioning
failure record — at which point, per Fable's own standing recommendation,
this line of work should stop rather than search for a 5th construction.
