## The source strategy

Externally-sourced (attributed to "Rajesh Jain", unverifiable — evaluated on
substance, not authority, same standing practice as every other externally-
sourced idea this project has taken in, e.g. candidates 14/15). The original
extracted spec described three setups against the day's official open price
on individual Nifty200 Momentum 30 stock options:

- **Setup A**: 09:15 1-minute candle's low == day's open → bullish → buy CALL.
- **Setup B**: 09:15 1-minute candle's high == day's open → bearish → buy PUT.
- **Setup C**: a "cross-back-through-open" pattern.

**Setup C is excluded from this methodology and backtest.** Every mention of
it across the feasibility doc and probe scripts (`grep`-checked before writing
this doc) is the same seven words — "the cross-back-through-open pattern" —
and no more precise rule was ever recorded from the original source. Building
a backtestable rule for it now would mean inventing a strategy, not testing
the one that was actually described. This is a disclosed scope reduction, not
a silent one: this candidate's verdict below covers Setups A and B only.

## Universe

`agent/universe_nifty200momentum30.txt` — NSE's published NIFTY200 Momentum 30
index, current constituents used as a fixed backtest universe. Same
survivorship-bias caveat already accepted for this candidate in the
feasibility doc (and the same class of limitation that closed the
index-reconstitution candidate) — today's constituent list is not
necessarily who was in the index on each historical trading day. Not
re-litigated here; a materially different problem (fixing it) than this
document's scope (pricing the strategy's real friction).

**SAIL is excluded from the universe**, not filtered day-by-day. The real
at-open probe measured SAIL's round-trip spread on 10 independent readings
across multiple days: 106.4%, 179.7%, 106.4%, 179.6%, 158.2%, 191.7%, 78.3%,
29.6%, 168.8%, 88.3% — a confirmed, persistent, essentially-no-real-market
case, not a hypothetical one a same-day liquidity filter might or might not
catch. Every other constituent stays in, unfiltered, even where a single
reading was noisy (e.g. CUMMINSIND's one 24.14% outlier against a 1.48%
reading three minutes later — kept in, since the *aggregate* cost model below
already accounts for this kind of noise via a project-wide median rather than
a per-symbol threshold).

## Session definition

Regular NSE session. This strategy only ever operates in the **09:15–09:30
IST** window — the opening 15 minutes — unlike every prior candidate's
full-session design.

## Entry signal

Per stock, per day, using that day's 1-minute candles:

- `day_open` = the 09:15:00–09:15:59 IST candle's `open`.
- Setup A: that same candle's `low == day_open` (tick-exact) → CALL.
- Setup B: that same candle's `high == day_open` (tick-exact) → PUT.
- If both fire on the same candle (a degenerate zero-range candle, i.e.
  `open == high == low`), the signal is ambiguous — **no trade**. A new,
  disclosed tie-break; the original spec did not address this case.
- At most one setup per stock per day, by construction (a single decision
  point, the 09:15 candle) — this is what the source spec's own "per-symbol
  Good Night lock after any exit" language amounts to here; there is no
  re-entry mechanism to lock against in this design.
- **Execution**: at the **open of the next 1-minute candle** (09:16:00–09:16:59
  IST's open) — no same-bar execution, same close-only/no-lookahead
  discipline as every prior candidate. This is a disclosed simplification of
  the spec's literal "09:15:30–09:18:00 IST" entry window (the same
  simplification the feasibility probe already used): Fyers' history endpoint
  has no access to a still-forming candle, so a backtest can only execute at
  a fully-closed candle's open, not mid-candle at 09:15:30.
- A day with fewer than 2 closed 1-minute candles available in the window
  (e.g. a shortened session) produces no signal for that symbol that day —
  skipped, not approximated.

## Exit management

- **Target**: entry premium × 1.10 (+10%).
- **Stop**: entry premium × 0.85 (−15%).
- **Time flatten**: 09:30:00 IST, regardless of target/stop status — this
  strategy's entire holding window is the last ~14 minutes of the opening
  range.
- Checked **every 1-minute candle** from entry to 09:30 IST via the premium
  reconstruction below (not the underlying's own price — the exit condition
  is native to the option premium, unlike candidate 18's index-points stop).
  Each candle contributes exactly one premium reading (from its `close`, no
  intrabar high/low) — since target_level (entry × 1.10) is always strictly
  above stop_level (entry × 0.85), a single reading can satisfy at most one
  of the two, so unlike candidates 15/18 there is no same-candle ambiguity
  to tie-break here.
- No trailing stop, no partial exits — a single target/stop/time-flatten
  bracket, matching the source spec's own framing (this is a fast scalp, not
  a trend-following trade).

## Contract selection

- **Expiry**: nearest **monthly** contract (stock options are monthly-only,
  confirmed live in the feasibility probe — unlike NIFTY's weekly cadence).
  **DTE floor**: if days-to-expiry on the entry date is `< 2`, roll to the
  *next* monthly contract instead — the source spec's own stated floor.
  Per the feasibility probe, this rarely binds (~1-2 days/month/stock).
- **Strike**: nearest ATM to the entry-candle's open, fixed at entry, never
  re-struck. **Strike interval is measured per symbol**, not assumed uniform
  (unlike NIFTY/BankNifty's fixed 50pt/100pt) — read once per symbol from a
  live option-chain fetch at backtest setup time (the minimum gap between
  consecutive listed strikes), then held fixed for that symbol's whole
  backtest window. A one-off "confirmed live" measurement, same convention
  as candidate 18's NIFTY/BankNifty constants.
- **Lot size**: per symbol, via `core/options/fyers_symbol_master.py`'s
  `get_lot_size()` — not a project-wide constant, since it varies by stock.

## Premium reconstruction

Same Black-Scholes approach as candidates 15/18
(`core/options/greeks.py::compute_greeks()`), with **one necessary
departure**: those candidates used India VIX as a shared IV proxy for
NIFTY/BankNifty. There is no equivalent single "stock VIX" for 30 different
individual names spanning banking, auto, pharma, and infrastructure — using
India VIX for all of them would misprice every stock whose own volatility
character differs from the index's.

**IV proxy: trailing 20-trading-day realized (historical) volatility** of the
stock's own daily close-to-close log returns, annualized
(`stdev(log_returns) * sqrt(252)`), computed strictly from daily closes
**before** the trade date (no lookahead) — a new, disclosed proxy choice.
Realized vol is not implied vol (no skew, no forward-looking risk premium),
the same class of approximation as every synthetic-premium candidate before
it, just a different proxy source because no per-stock IV series exists.

Reconstructed at entry and at every subsequent 1-minute candle through exit,
using the underlying's real 1-minute closes for `spot` — same "contemporaneous
inputs, not frozen at entry" discipline as candidates 15/18.

## Cost model

**Clean**: `core/options/vrp/costs.py`'s time-varying STT/exchange rates,
composed via `core/risk/costs.py`'s `CostModel.round_trip()` — identical
machinery to candidate 18's `clean_trade_cost()`, zero slippage.

**Stressed**: Clean plus a slippage rate derived from **real measured data**,
not a guessed bps range — this candidate has something candidate 18 never had
pre-verdict: a recurring, multi-day, at-the-actual-entry-window live spread
sample. `quantos-goodnight-openwindow-probe.timer`, 2026-09-04 through
2026-09-15 (7 trading days; 2026-09-16/17 lost to a stale VM Fyers token, a
separate operational gap, not a data quality issue), 242 individual CE/PE
legs across the universe (SAIL's 10 readings excluded, per the universe
exclusion above): **median round-trip spread 2.09% of premium**. Converted to
`CostModel`'s per-leg `slippage_bps` convention the same way candidate 18's
`costs.py` does it (`slippage_bps = 50 * round_trip_spread_pct`, since
`CostModel` charges the bps rate on both the buy leg's and sell leg's own
turnover): **`GOODNIGHT_STRESSED_SLIPPAGE_BPS = 104.5`**.

Both numbers are reported side by side, pooled across the whole universe
(Setup A + B together — see Validation below for why these are not split).
**The Stressed result is the one that gates any move toward live capital** —
same rule as candidate 18, and a stricter one is warranted here: this
candidate's Stressed number is a real measured median from 7 independent
mornings, not a stress-tested assumption layered onto a clean model.

## Position sizing

1 lot per trade — simplest literal implementation, same as every prior F&O
candidate.

## Backtest window

Depth is capped by Fyers' 1-minute retention wall, confirmed **at least 70
calendar days** back per the feasibility probe (2026-09-03) and **not
confirmed beyond that** — unlike candidate 18, this candidate cannot fall
back to a coarser resolution (the signal is only meaningful at 1-minute
inside a 15-minute window), so this is a hard ceiling on sample size, not a
choice. **Re-verified at run time by the actual fetch** (same discipline as
every prior candidate) rather than re-asserted blindly — the backtest script
starts from the confirmed 70-day floor and walks backward only as far as
real data actually returns.

**This is a small-sample candidate, disclosed up front, same class of risk
that shelved the PEAD candidate.** At a ~28% observed hit rate (feasibility
probe) across ~29 non-SAIL symbols over roughly 45-50 trading days once the
20-day realized-vol lookback buffer is subtracted, the expected trade count
is on the order of 300-400 — larger than PEAD's shelving sample, but still a
single ~2-3 month window covering one volatility regime, not a
representative cross-section of market conditions across cycles. Read any
result with that in mind; a pass here is a real, actionable finding, but a
smaller-sample one than candidate 18's multi-year verdict.

## Validation criterion / pass-fail bar

**Same bar used throughout this project**: `core/backtest/parser.py`'s
`has_positive_edge` — profit factor > 1.0 AND Sharpe > 0.5 — on the pooled NET
(post-cost) trade set.

**Pooled across the whole universe and both setups (A and B together), not
split per symbol or per setup.** This differs from candidate 18's explicit
"never pooled" rule for NIFTY/BankNifty — those are two structurally
different instruments (different liquidity, different expiry cadence,
different lot sizes) where pooling would hide a real divergence. Setups A and
B here are mirror images of the same mechanical rule on the same universe of
instruments, and a real trader running this strategy trades the whole basket,
not one symbol or one setup in isolation — pooling matches how it would
actually be traded. Per-setup (A vs B) and per-symbol trade counts are
reported alongside as supplementary breakdowns, not as separate gates.

**Reported alongside the pooled number**: a per-month breakdown (not
per-year — the window is too short for that to be meaningful), bounded by
whatever window the live depth-fetch actually confirms.

## What would make this validation untrustworthy after the fact

- Changing the entry tick-match rule, the next-candle execution timing, the
  +10%/-15%/09:30-flatten exit bracket, the DTE floor, the ATM strike rule,
  or the 20-day realized-vol lookback, after seeing a weak or strong result.
- Excluding any symbol other than SAIL after seeing results (SAIL's exclusion
  is locked here, before any result, on the confirmed-live evidence already
  in hand — no other symbol gets that treatment retroactively).
- Reporting only Clean and omitting Stressed, or treating a Clean-only pass
  as sufficient to move toward live capital.
- Splitting NIFTY200-momentum-30-style per-symbol or per-setup results into
  separate gates after the fact, cherry-picking whichever subset passed.
- Silently narrowing the backtest window to whatever the depth probe finds
  convenient, without recording the probe's actual finding here first.
- Building Setup C after a weak Setup A/B result and calling it the same
  candidate rather than a freshly pre-registered one that discloses it was
  built in response to this candidate's specific outcome.
